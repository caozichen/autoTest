# Runner 管理资源自动刷新

## 行为

- 资源区按钮按“手动刷新”“自动刷新”的左右顺序排列；开启后右侧变为“停止自动刷新”，采集中仍可停止。
- 首次进入采集一次，自动刷新默认关闭。开关仅保存在当前应用的 Pinia 内存中，站内切页保留，整页重载或应用重新启动后关闭。
- 开启时立即采集，之后每次采集完成等待 1 秒再更新。健康检查与资源请求必须全部结束才安排下一轮，各自保留 2 秒超时；慢请求、失败和手动刷新不会叠加轮询。
- 只保留最新资源快照，使用浅层响应式引用；失败保留上次成功快照并标记过期，后续成功自动恢复。
- 离开页面时清理定时器、取消未完成请求、移除可见性监听；后台标签暂停采集，返回后按保留的开关恢复。后台首次打开时延后至可见时采集。
- 停止自动刷新会取消本轮自动请求；取消后的迟到结果不写入界面。手动采集仍可单独使用。

## 验证

- `npm run test --workspace @autotest/web`：41 个文件、320 项通过。新增每秒刷新、停止、路由重挂载、新应用默认关闭、慢请求／提前失败不重叠、取消及迟到响应、后台暂停与首次可见采集等覆盖。模拟 10 分钟刷新及 30 次开关切换后，最多仅一个调度定时器，DOM 数量不变，停止／卸载后无定时器。
- `node --test apps/api/runner-resources-browser.test.mjs apps/api/runner-resources.test.mjs`：5 项通过，使用安装的 Google Chrome 和临时 Runner／存储；业务执行尝试为 0。
- `npm run typecheck`、`npm run build` 和 `git diff --check` 通过。构建仍有已有公共分包超过 500 kB 和依赖注释提示。
- Chrome 验证默认关闭后静置 6 秒无请求，开启、停止、离线及恢复、切页保留和离页暂停、重新加载默认关闭；1440／900／390 px 下无页面或指标横向溢出，按钮保持手动在左、自动在右；页面异常为 0。桌面和窄屏截图已查看。

## 性能观察

完整数值及截图保存在 `outputs/reports/2026-10-26-runner-auto-refresh/`，其中 `browser-validation.json` 为原始数据。

| 项目 | 实测 |
| --- | --- |
| 连续自动刷新 | 60.11 秒内 60 次资源采集，同时各做一次健康检查 |
| 20／40／60 秒 GC 后浏览器 JS 堆 | 8.99／9.08／9.11 MiB |
| 上述三个采样点的 DOM 节点／监听器 | 均为 945／116 |
| 浏览器渲染进程任务耗时占观察时长 | 约 1.54%，包含测试测量开销，不等于整机 CPU |
| Runner 内部资源采集耗时 | 平均 0.65 ms，最大 2.05 ms |
| 20 次快速往返切页后，等待 1 秒清理并 GC | 945 个节点、116 个监听器、堆约 10.13 MiB |

首轮浏览器检查在快速切页后立即测量，捕获到 3701 个节点、244 个监听器，未通过原有严格界限。检查 Element Plus 实现确认加载遮罩存在 400 ms 退出清理；复核记录即时及清理后的数值，并在等待 1 秒后按相同界限验证。最终复核从即时 3706 个节点／244 个监听器恢复为 945／116，未发现持续残留。

这次观察覆盖临时环境的一分钟真实刷新、20 次切页和模拟 10 分钟调度，未出现内存溢出或请求累积。采样器不会加载历史详情；测试未访问真实历史或执行业务任务。上述结果不代表对任意业务负载或无限运行时间的内存保证。
