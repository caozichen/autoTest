## “报错但答卷已保存”能否自然发生

可以，从当前源码可以确认存在这条路径；此结论不等于本次已在 TEST 复现。

- `lx-global-backend/app/Services/Form/Client/FormService.php:337` 开启答卷事务，事务在 `:433` 前结束。
- 事务之后发出保存事件，分发活动等业务；支付场景还会创建订单。
- `FormService.php:485` 构造响应时才调用 `SubmissionResultTokenService::issueOrReuse()`，调用之外没有撤回答卷或上述业务的补偿处理。
- `SubmissionResultTokenService.php:171` 起通过 PhpRedis 执行 Lua，底层异常被转换成 `CacheUnavailableException`。缓存凭证解密或摘要核对失败也会抛出同类异常。
- `app/Exceptions/Handler.php:86` 将该异常转换为 **HTTP 503 Service Unavailable**，并保留可重试响应头；这里并非固定返回 500。

后台手动创建答卷通过 `$isAdminSubmission` 跳过结果凭证签发，因此这里讨论的是公开填写入口。

自然触发条件包括：前面步骤成功后、签发凭证时 Redis 连接中断、超时或切换；执行签发 Lua 时写入失败。已有缓存凭证无法解密或摘要不一致也会失败，但更直接对应凭证重用路径，不能据此断言每次新答卷都存在缓存旧值。

不是所有 Redis 故障都会产生已保存答卷：若请求早期依赖 Redis 的校验或预占已经失败，请求可能根本未进入提交事务。问题条件是事务及前面操作已成功，而响应凭证阶段失败。

用户可能看到提交失败，数据库实际已有答卷；允许重复提交时再次操作可能新增答卷及关联业务。判重规则或已消费的协议确认令牌可能阻止重试，却仍无法给用户第一次提交的查看凭证。本次只修改自动化断言，没有修复后端这一一致性问题。
