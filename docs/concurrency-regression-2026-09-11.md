# 三环境并发改造与回归记录

日期：2026-09-11。基于当天更新的后台流水线实现继续改造，保留已有代码、三个配置和步骤顺序。本记录对应“增加自动化程序并发功能”提交的验收结果。

## 实现行为

- 单个 Runner 支持最多三个流水线批次并发，批次内部按既有顺序执行。不同环境可共享脚本，也可同时运行同一个配置。
- 环境快照、Token、变量、步骤输出、运行 ID、取消信号和制品目录按批次独立。同一环境内相同配置或共用脚本继续互斥，相同 API origin 的别名按同一环境处理；超出并发上限返回 429，不自动重跑。
- 流水线与普通脚本入口共享启动登记临界区，业务执行不占用该临界区；未完成保存和重启待恢复批次继续占用名额。
- 配置页显示所有后台批次、环境及当前步骤。配置行显示当前所选环境状态；切换环境后可启动另一个批次。
- 停止操作按批次 ID 定位。脚本对应多个运行批次时先选择目标；日志按环境选择，打开后固定所选批次。含糊的脚本取消请求返回 409，不停止任何批次。
- 保存失败的批次单独重试，其他批次继续保存。共用默认上传图片通过临时文件原子替换，避免并发首次生成时读到半成品。

## 第一轮发现的问题与修复

第一轮内地、测试六步全通过；香港六步执行完成，但名为“检查并编辑提报信息”的步骤有两条网络断言失败，原批次为 `a1189f7b-4bba-4bfc-add4-67be0dceae9c`。

两条失败分别为公开页地区树 `/api/area/tree` 和一张私有图片，在网络观察器收尾时仍未完成。证据显示这两个旧请求发于主动刷新前；刷新后的同资源请求均正常返回 200。原脚本做完第一页空表校验就立即刷新，慢请求可能被新文档替换，留下未完成的采集状态。不能据此认定业务服务保存或提报失败。

修复在主动刷新前等待当前页面已发出的接口正文和资源加载完成，使用当前环境的导航超时预算。等待超时则停止刷新及后续提报，保留网络失败证据；未增加业务写操作重试，也未放宽断言或丢弃未完成请求。新增测试用延迟地区树正文和图片验证刷新前完成加载，同时验证等待超时仍记录失败、等待后继续采集新文档证据。修复后重跑全量测试和三个真实环境的完整并发批次，结果如上。

三个真实环境通过后，全量回归中的脚本规范检查指出新增的刷新保护使用了普通异常。已按项目约定改为明确的流程阻塞断言 `flowExpect(...).toBe(true)`，保留相同的等待预算、成功条件及超时停止行为；随后再次运行全部测试并通过。该最后调整只涉及保护的表达方式，未再次创建真实环境批次。

第一轮结果未覆盖或删除，保存在 `outputs/concurrency-20260911/first-pass-summary.json`；最终结果保存在同目录的 `three-environment-summary.json`。完整日志为 `full-test.log`，慢加载专项日志为 `reload-regression.log`，规范检查修复前的失败日志为 `full-test-before-flow-guard-fix.log`。

## 现有配置的验收边界

当前三个配置中，名为“检查并编辑提报信息”的注册脚本 ID 是 `form-all-fields-submit`，入口为 `form-all-fields-submit.ui.spec.mjs`，请求路径为 `/form/?id={{FORM_ID}}`。代码实际委托公开表单填写并再次提交，不是编辑已有提报。

本次按用户要求保留现有配置及行为，没有替换这个入口。因此上面的三环境验收证明的是当前配置实际执行的流程，不能把该步骤名称视为真实“编辑提报”功能已在三个环境验收。仓库另有 `form-submission-reply-edit.ui.spec.mjs`，其本地 Chrome 测试已随全量回归通过；如果要让配置执行真正的编辑操作，需要单独调整脚本登记、详情页路径和提报 ID 传参。

## 使用

在自动化配置页选择对应环境，运行对应的冒烟配置，然后切换环境继续启动下一条。后台最多同时保留三个运行批次；使用“停止此批次”可单独停止一个。单 Runner 的并发能力不等同于多进程或多机器共享文件存储。
